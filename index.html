Software testing strategies, explained simply

A study guide for students and anyone preparing for QA or SDET interviews. Start with the testing pyramid: tap a layer to see what it tests, who writes it and which tools are used.

Top: fewer, slower, costlier tests. Base: more, faster, cheaper tests.

The basics

Testing checks whether software does what it should and finds problems before users do. It reduces risk; it can never prove software is bug-free.

QA vs QC vs testing

Quality assurance (QA) improves the process so defects aren't made (reviews, standards). Quality control (QC) checks the product for defects. Testing is the main QC activity.

Remember: QA prevents, QC detects.

Verification vs validation

Verification: "Are we building the product right?" Reviews, walkthroughs, static checks against the spec.

Validation: "Are we building the right product?" Running the software to see it meets user needs.

Error, defect, failure

A person makes an error (mistake) → it leaves a defect (bug) in the code → running that code causes a failure the user sees.

Example: developer types > instead of >= → age 18 is rejected → a valid user can't sign up.

Static vs dynamic testing

Static: examine without running (code reviews, requirement reviews, linters). Dynamic: execute the code with inputs and compare results.

The 7 testing principles (ISTQB)

PrincipleWhat it means in practice
Testing shows the presence of defectsTests can find bugs, but passing tests don't prove there are none.
Exhaustive testing is impossibleYou can't test every input; use risk and test design techniques to choose.
Early testing saves time and moneyA bug found in requirements costs far less than one found in production (shift-left).
Defects cluster togetherA few modules usually hold most bugs; test those harder.
Tests wear out (pesticide paradox)Running the same tests again stops finding new bugs; review and add tests.
Testing is context dependentA banking app and a game need different testing.
Absence-of-errors fallacyBug-free software that doesn't meet user needs is still a failure.

Software Testing Life Cycle (STLC)

STLC is the set of phases testing goes through inside the development life cycle (SDLC). Each phase has entry criteria (what must be ready to start) and exit criteria (what must be done to finish).

  1. Requirement analysisStudy requirements, ask questions, find what's testable. Output: requirement traceability matrix (RTM).
  2. Test planningScope, approach, effort, schedule, tools, risks, roles. Output: test plan.
  3. Test case designWrite test cases, test data and automation scripts. Output: reviewed test cases.
  4. Environment setupPrepare test servers, data and builds; run a smoke test.
  5. Test executionRun tests, log defects, retest fixes, run regression.
  6. Test closureCheck exit criteria, report metrics, record lessons learned.

Types of testing

Functional testing checks what the system does. Non-functional testing checks how well it does it: speed, security, usability.

Commonly confused pairs

PairDifference
Smoke vs sanitySmoke: broad, shallow check that a new build is stable enough to test. Sanity: narrow check that a specific fix or feature works.
Retesting vs regressionRetesting: confirm a specific fixed bug is fixed (same steps). Regression: confirm the change didn't break anything else.
Load vs stressLoad: expected peak users. Stress: beyond the limit, to find the breaking point and how it recovers.
Exploratory vs ad hocExploratory: structured, time-boxed with a charter, learning while testing. Ad hoc: informal, no plan or documentation.
Black box vs white boxBlack box: tests from requirements, no code knowledge. White box: tests designed from the code's structure.

Development methodologies and where testing fits

The methodology decides when testing happens. The modern trend is earlier and continuous: test in every sprint and in every pipeline run.

Shift-left

Move testing earlier: review requirements, write tests before or with code, run unit and API tests in CI.

Shift-right

Keep testing after release: monitoring, canary releases, A/B tests, feature flags, production smoke checks.

TDD

Test-driven development: write a failing unit test → write just enough code to pass → refactor. "Red, green, refactor."

BDD

Behavior-driven development: describe behavior in plain language (Gherkin) that business, devs and QA share.

Given a registered user When they enter a wrong password 3 times Then the account is locked

ATDD

Acceptance test-driven development: the team agrees on acceptance tests before building the story.

Agile testing quadrants

Q1 unit/component (tech, supports team) · Q2 functional/story tests · Q3 exploratory/usability/UAT · Q4 performance/security.

Test design techniques

Since you can't test everything, these techniques pick the few tests most likely to find bugs. Every example below uses one rule: age must be between 18 and 60.

Equivalence partitioning

Split inputs into groups the system treats the same; test one value from each.

Partitions: under 18 (invalid), 18–60 (valid), over 60 (invalid). Tests: 10, 35, 70.

Boundary value analysis

Bugs hide at the edges. Test on and just beyond each boundary.

Tests: 17, 18, 60, 61 (two-value). Add 19 and 59 for three-value BVA.

Decision table

For combinations of conditions; one column per rule.

Login: valid user + valid password → home page · valid user + wrong password → error · unknown user → error.

State transition

For systems whose behavior depends on their current state.

ATM PIN: wrong PIN once → try 2 · twice → try 3 · three times → card blocked.

Pairwise testing

Test every pair of options instead of every combination.

3 browsers × 3 OS × 2 languages = 18 combinations, covered by about 9 pairwise tests.

Use case / scenario

Test end-to-end user journeys, including alternate and error paths.

Checkout: add to cart → pay → confirm; plus card declined, out of stock.

White-box coverage

Statement: every line runs once. Branch/decision: every if is both true and false. Path: every route through the code.

100% branch coverage guarantees 100% statement coverage, not the other way round.

Experience-based

Error guessing: try what usually breaks (empty, null, special characters, huge input). Exploratory: learn and test at once, guided by a charter.

Test strategy vs test plan

The strategy is the organisation's or product's long-term approach to testing. The plan applies it to one project or release: who, what, when.

Test strategyTest plan
LevelOrganisation or product, high levelProject or release, detailed
ChangesRarelyOften, as the project changes
Written byQA manager or leadTest lead with the team
ContainsTest levels and types, automation approach, tools, environments, risk approach, metricsScope (in/out), schedule, resources, entry/exit criteria, deliverables, risks and mitigation

Entry criteria

Requirements signed off, build deployed to test environment, smoke test passed, test data ready.

Exit criteria

Planned tests executed, pass rate target met (for example 95%+), no open critical or high defects, regression passed, sign-off given.

Risk-based testing

Rank features by likelihood of failure × business impact. Test the highest-risk areas first and deepest; payments before profile photos.

Release readiness

Go/no-go checklist, rollback (backout) plan tested, post-deployment smoke test in production, release notes from QA.

A good bug report has

Clear title · environment and build · steps to reproduce · expected vs actual result · severity and priority · screenshots, logs or video · test data used.

Test metrics

Metrics turn testing into numbers leaders can act on. Know these formulas for interviews.

Defect removal efficiency

DRE = defects found before release ÷ (before + after release) × 100

Example: 90 found in testing, 10 in production → 90%.

Defect leakage

Leakage = defects found in production ÷ defects found in testing × 100

Example: 10 ÷ 90 → about 11%.

Defect density

Density = defects ÷ size (KLOC, modules or story points)

Shows which module needs more attention.

Automation coverage

Coverage = automated test cases ÷ total automatable test cases × 100

Pass rate

Pass rate = passed ÷ executed × 100

Also tracked

Test execution progress, defect age (time open), mean time to detect and to fix, flaky test rate, escaped defects per release.

Automation strategy

Automate what's repeated, stable and high-value. Keep humans on exploration, usability and anything that changes every week.

Framework types

Linear (record/playback) · Modular · Data-driven (same test, many data rows) · Keyword-driven · BDD (Cucumber) · Hybrid (most real frameworks).

Page Object Model

Each page is a class: locators are private, actions are public methods. Tests read like user steps and a UI change is fixed in one place.

Flaky tests

Pass and fail without code changes. Causes: fixed sleeps, timing, shared test data, test order, environment. Fix with explicit waits, isolated data and independent tests; quarantine until fixed.

In the CI/CD pipeline

Commit → unit tests → build → API tests → deploy to test env → UI smoke → full regression nightly → deploy → production smoke.

Common tools

UI: Selenium, Playwright, Cypress · API: REST Assured, Postman · Unit: JUnit, TestNG · BDD: Cucumber · Performance: JMeter · CI: Jenkins, GitHub Actions · Reports: Allure.

Measuring ROI

Compare time to build and maintain the automation against manual hours saved per run × runs per release. Maintenance is the hidden cost.
